# Versioning and releases

Project 3DS follows [Semantic Versioning 2.0.0](https://semver.org/) and uses
git tags as the only source of truth.

## Tag format

A release tag is `vMAJOR.MINOR.PATCH`, optionally followed by a pre-release
suffix:

```
v0.1.0
v0.2.0
v0.2.1
v0.3.0-rc.1
v0.3.0-beta.2
```

Once a tag has a GitHub release, it must not be moved, deleted or reused.
Build metadata (`+g3a97fc3`) is only added to development builds and never
appears in a tag.

## Versions in builds

`build.sh` asks `tools/version.sh` for the version and passes it to the build as
`APP_VERSION`. The Makefile puts it in the SMDH long description, so the
installed title carries the version in its metadata:

```
APP_DESCRIPTION := v$(APP_VERSION)
```

`tools/version.sh` derives a semver-compatible value from the nearest tag:

| Checkout state | Version |
| --- | --- |
| exactly on `v0.1.0` | `0.1.0` |
| three commits after `v0.1.0` | `0.1.1-dev.3+g3a97fc3` |
| the same tree with local changes | `0.1.1-dev.3+g3a97fc3.dirty` |
| after `v0.2.0-rc.1` | `0.2.0-rc.1.dev.3+g3a97fc3` |
| no tag yet | `0.0.0-dev.1+g3a97fc3` |
| outside a git checkout | `0.0.0-dev` |

Print the version of the current checkout without building:

```sh
./build.sh version
```

A source archive has no git metadata, so its version is `0.0.0-dev`. Set
`APP_VERSION` explicitly to override the derived value.

## Publishing a release

Releases are built and published by
[`.github/workflows/release.yml`](../.github/workflows/release.yml) when a tag
is pushed.

1. Make sure `main` is green and the release notes are ready.
2. Create an annotated tag on the release commit:

   ```sh
   git switch main
   git pull
   git tag -a v0.1.0 -m "Project 3DS v0.1.0"
   ```

3. Push only the tag:

   ```sh
   git push origin v0.1.0
   ```

The workflow then:

- checks that the tag is a valid semantic version and points at `HEAD`;
- checks that the tagged commit is on `main`, so an unreviewed branch cannot
  be released;
- checks that the tag and the derived `APP_VERSION` agree;
- runs the test suite;
- builds `project-3ds.3dsx` and `project-3ds.cia`;
- publishes `project-3ds-v0.1.0.3dsx`, `project-3ds-v0.1.0.cia`,
  `project-3ds-v0.1.0.zip`, the licence and notice files, and `SHA256SUMS`.

The zip contains both binaries together with `README.md`, `LICENSE`,
`NOTICE.md`, `THIRD-PARTY-NOTICES.md`, `LICENSE-Liberation.txt` and the release
documentation, so the notices travel with the binaries.

Tags with a pre-release suffix are published with the pre-release flag. The
release notes link to the source code at the tag, which is the corresponding
source for the binaries.

### Pinned toolchain

`DKP_IMAGE` pins the build image by digest, because the image tag alone does not
identify a toolchain: the binary that produced a release has to be the binary
recorded for it. The digest belongs to the multi-architecture image, so the
runner picks the right one for its platform. Bump it deliberately and mention
the change in the release notes:

```sh
curl -fsS https://hub.docker.com/v2/repositories/devkitpro/devkitarm/tags/latest \
  | python3 -c 'import json,sys; print(json.load(sys.stdin)["digest"])'
```

### Verifying a download

`SHA256SUMS` is generated by the workflow and covers every published file, so it
detects a truncated or corrupted download:

```sh
sha256sum --check --ignore-missing SHA256SUMS
```

It is produced by the same job that produces the binaries, so it does not prove
who built them. Signing the sums with a key held outside CI is the next step;
until then the sums protect against a corrupted or truncated download, not
against a malicious release.

## If a release fails

- If the workflow failed before publishing, re-run the failed workflow from the
  Actions tab. Do not delete the tag. The release is still a draft, so the
  assets are uploaded again and the draft is published at the end.
- If the release was published, its assets and tag are locked. A re-run only
  succeeds when the rebuild is byte-for-byte identical, in which case there is
  nothing to upload.
- If the released binaries are broken, or the fix changes the build, publish a
  new `PATCH` release. Users who already downloaded the old build can then tell
  the two apart from the version in the description.
